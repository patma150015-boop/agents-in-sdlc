最初に、小さな機能をプロジェクトに追加しました。しかし、より大規模な変更には堅牢なプロセスが必要です。GitHub Copilot app は、組織の既存の開発フローに沿って作業し、適切なものを適切な方法で構築できるように設計されています。このレッスンから続く複数のレッスンで、Issue から新機能を作成し、コードと動作を検証して、最終的にプロジェクトにマージする、一般的なエージェント主導の開発プロセスを実践します。

> [!NOTE]
> 機能のワークフローを進める間は、同じセッションを使用します。通常は作業するファイルの種類ごとに異なるセッションや pull request (PR) を使いますが、ここでは中心となる概念に集中できるように手順を短縮します。

このレッスンでは、次のことを行います。

- GitHub Issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動検証します。

この機能の作業を続ける間に、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズし、Model Context Protocol (MCP) による検証を追加し、品質保証 (QA) エージェントを作成して、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが充実し、訪問者がカテゴリーとパブリッシャーでゲームを絞り込める機能が必要になりました。バックログの Issue に機能は記載されていますが、複数カテゴリーの組み合わせ方などはコーディング前に合意が必要です。Plan モードで決定事項を整理してから、Autopilot による範囲を限定した実装を承認します。

## 背景

人工知能 (AI) コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のようなフローに従います。

1. 必要な作業の詳細が記載された Issue を開きます。
2. 構築する内容の計画を作成します。
3. コードを構築してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. PR を作成します。
7. コードのレビューと継続的インテグレーションプロセスが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを変形したものです。

この標準的なアプローチを守ることで、AI が生成したコードが定められた要件を満たし、人間が作成したコードと同じ審査プロセスを通るようにできます。

## セッションモード

**セッションモード**は、エージェントの自律性を制御します。プロンプトフィールド下のドロップダウンから設定し、いつでも変更できます。

- **Interactive**: 開発者とエージェントが共同で作業します。エージェントは変更を提案し、続行前に開発者の入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。計画を実行する前に、内容をレビューして承認します。
- **Autopilot**: エージェントが完全に自律して作業し、入力を待たずにコードの作成、テストの実行、反復を行います。

Plan モードで開始し、計画をレビューしてから、Autopilot で実装します。

## Issue からセッションを開始する

星評価の PR がマージされ、ローカルの `main` が最新であることを確認してから、新しいセッションを開始します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。既存のシード済み Issue **Allow users to filter games by category and publisher** を開きます。新たに Issue を作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の Issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは実行できてもセッションで見つからない場合は、アプリの PATH やバージョンマネージャーの設定を確認し、アプリを完全に終了してから再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで、npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したため、Copilot は機能リクエストをすでにコンテキストとして持っています。計画が Issue の受け入れ条件を満たすことを確認し、要件の曖昧さを解消してから承認します。

1. 次のプロンプトを Copilot に送信します。

    ```plaintext
    Build this feature.
    ```

2. Copilot の質問に回答し、カテゴリーとパブリッシャーによる絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが計画に含まれていることを確認します。
3. 複数カテゴリーの組み合わせや、一致するゲームがない場合の動作など、不明確な点について話し合います。
4. プロジェクトの既存ツールを使った lint、単体テスト、エンドツーエンド (E2E) テスト、型チェックが計画に含まれていることを確認します。計画をフィルター機能の実装とテストに絞り、PR は品質ワークフローの完了後に作成します。
5. 必要に応じて計画の修正を依頼し、承認する前に内容を確定します。後の検証に使えるよう、Issue の URL (Uniform Resource Locator) と合意した明確化事項を控えておきます。

## Autopilot を明示的に承認する

計画のレビューが完了したら、Autopilot で実装を開始します。

1. **Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。
2. 承認しただけでモードが切り替わるとは限らないため、モード表示が **Autopilot** になっていることを確認します。

Copilot が実装を開始し、計画に沿ってコードの生成やテストを行いながら反復します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェックを完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードも、他のコードと同じようにマージ前にレビューする必要があります。コードをレビューし、サイトを実行して問題がないことを確認します。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリーとパブリッシャーの組み合わせも含め、結果を Issue と承認した明確化事項に照らし合わせます。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、単体テスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカルサーバーを再利用できます。テスト対象が以前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動くか確認します。前と同じようにアプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリーを選択し、結果が一致することを確認します。フィルターをクリアしてからパブリッシャーを選択し、結果がそのパブリッシャーに一致することを確認します。
4. カテゴリーとパブリッシャーのフィルターを組み合わせ、結果を Issue と承認した計画に照らし合わせます。複数カテゴリーがサポートされている場合は、合意した組み合わせ動作を確認します。
5. 一致するゲームがない条件を試し、空の状態を確認します。フィルターをクリアまたはリセットし、全件が再表示されることを確認します。
6. 確認が終わったら、次のプロンプトを使い、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンに向けて同じセッションを保持する

この後の作業でも、同じ作業環境を再利用します。フィルター機能の PR はまだ作成またはマージしないでください。

1. セッション、worktree、ブランチをレッスン 4 から 8 まで保持します。次はフィルター機能のコードにカスタム指示を適用し、その後スキルと QA の改善を加えて、レッスン 8 でまとめた PR を作成してマージします。
2. 開発サーバーを停止した後はセッションをそのままにし、次のレッスンで同じセッションに戻ります。

## まとめと次のステップ

さまざまなエージェントモードを使って、機能を構築およびレビューしました。このレッスンでは、次のことを行いました。

- GitHub Issue から新しいエージェントセッションを開始しました。
- **Plan** モードで要件を定義しました。
- **Autopilot** モードで新機能を実装しました。
- コードをレビューしました。
- ブラウザーキャンバスで機能を手動検証しました。
